# Safeguarding data

Source: the founder's decision on #36 (26 October 2026), with Ezra's and Nadia's conditions. This is a recorded exception to SG6 and P5 until the M2c sunset.

- **Agents never query, export, migrate or otherwise touch the safeguarding databases.** That covers `kinmeet-live-safeguarding`, its made-up-data copies for staging and Previews (`kinmeet-*-safeguarding`), and the `SAFEGUARDING_DB` binding. It applies to `wrangler d1` (`execute`, `export`, `migrations`, `time-travel`, `info`, `delete`), the Cloudflare API, the Cloudflare MCP tools and any script that would reach them. Until M2c, these databases hold disclosures in plain text, and only the acting safeguarding lead reads them, through the app.
- **Why:** the team's Cloudflare connection is account-wide and can reach any D1 database. Without this rule, an agent could read a disclosure about a child. The founder accepted the interim store only on this condition.
- **Code may name the binding.** Building and testing `server/safeguarding/` is fine. To search the code for it, use the Grep tool: any Bash command that names a safeguarding database is refused, apart from commit messages and PR or issue text. Use the Vitest Workers pool with migrations applied in test setup, never a real database. Only `server/safeguarding/` may use `SAFEGUARDING_DB`.
- **Ids stay out of the repository.** Safeguarding database ids are not committed. An account admin can list them for the hooks in `KINMEET_SAFEGUARDING_DB_IDS` or `~/.kinmeet/safeguarding-db-ids`. `wrangler d1`, the D1 MCP tools and D1 API calls only accept the `DB` binding or a main database name or literal id listed in `wrangler.jsonc`. A database worked out at run time (a shell variable, or listing the databases and looping over them) is refused.
- **Hooks enforce this** (`guard-bash.mjs` and `guard-cloudflare.mjs`, tested in `bun run test:hooks`). They are a safety net, not the control. Never work around one. If you think you need access, stop and tell your EM. The answer goes to the safeguarding lead, not to you.
- Schema changes to the safeguarding databases ship only as reviewed migrations applied by the deploy, and the one-off removal at the M2c sunset is the same.
