# ADR-0009: Adopt NuxtHub, keeping our Worker entry, environments and migrations

- **Status:** Proposed
- **Date:** 27 October 2026
- **Author:** Priya Nandakumar (Engineering Manager)
- **Reviewers:** Theo Marsh (Tech Lead), Jun Okafor (DevOps Engineer), Nadia Haddad (Security Reviewer), Ines Duarte (Research Scout)
- **Related:** issue #113, the audit on #104 ([docs/research/nuxt-modules.md](../research/nuxt-modules.md), PR #107), ADR-0001, ADR-0002, ADR-0003, ADR-0008, [.claude/rules/existing-modules.md](../../.claude/rules/existing-modules.md), [.claude/rules/safeguarding-data.md](../../.claude/rules/safeguarding-data.md), P5

## Context

The founder has chosen to adopt NuxtHub (`@nuxthub/core`) now. The #104 audit recommended waiting, because of four gaps. This ADR closes each one, using a spike build of `@nuxthub/core` 0.10.11 on top of `main` (045fc2a). The spike was never pushed.

1. **`deployConfig` and environments.** NuxtHub turns on Nitro's `cloudflare.deployConfig`. Nitro then writes `.output/server/wrangler.json`, and Wrangler's redirected config (`.wrangler/deploy/config.json`) makes every later command in the project use that file. NuxtHub flattens one environment into it, chosen by the `CLOUDFLARE_ENV` build variable. The spike found one hazard: once the file exists, `wrangler deploy --env staging` ignores `--env` and gives no error. If `CLOUDFLARE_ENV` was not set at build time, a staging deploy would ship the top-level local config.
2. **The ADR-0008 Worker entry.** With `deployConfig` on, Nitro replaces our `main` with its own `index.mjs`, and only logs a warning. So `worker/index.mjs` would stop running, and nothing would limit request bodies.
3. **R2, KV and safeguarding bindings.** `hub:db`, `hub:kv`, `hub:blob` and `hub:cache` each add a binding to the generated config. `hub:cache` adds a new KV binding named `CACHE`. NuxtHub also sets `migrations_table` to `_hub_migrations` on the `DB` binding whenever we leave it blank. On staging and live, Wrangler would then think no migration had run and apply them all again. The separate safeguarding database is gone (#91 keeps an encrypted table in the main D1), so the only safeguarding binding is the `SAFEGUARDING_KEY` secret.
4. **libSQL compared with D1 in development.** Unless the driver is set, `hub:db` uses a libSQL file (`.data/hub/db/sqlite.db`) in development. That would mean development runs on a different engine from tests and production. In development NuxtHub also applies migrations itself, and records them in its own `_hub_migrations` table.

The other constraints still apply. `wrangler.jsonc` is kept by hand so that bindings are reviewed. Data stays in Europe. Nothing makes third-party requests. Only `server/safeguarding/` names the safeguarding table.

## Decision

Adopt `@nuxthub/core` for `hub:db` now, with Drizzle. Keep `wrangler.jsonc` as the only place bindings are written. Keep our body limits in front of Nitro. Keep Wrangler as the only tool that applies migrations, everywhere. Turn on `hub:kv` and `hub:blob` only when a feature first needs them, and keep `hub:cache` off.

### Conditions for phase 1 (Security Reviewer, on #114)

1. **Check the generated config, not only `wrangler.jsonc`.** A CI step builds, then checks `.output/server/wrangler.json`. Its binding list (names, ids and jurisdiction) must match a committed snapshot, so no binding appears without review. No binding in its `previews` block may name a live database, namespace or bucket. This guards against NuxtHub's flattening ever dropping or reshaping `previews`, which a test of `wrangler.jsonc` alone would miss.
2. **Wrangler is the only migration runner.** Never run `drizzle-kit push`, `migrate` or `drop` against a real database: the schema leaves out `safeguarding_items` on purpose, so these tools would treat it as something to drop. Phase 1 adds them to the Bash hook's refusals for anything that isn't local. In phase 2, the schema test expects `safeguarding_items` to be absent from the schema and present in the database.
3. **No `--env` in the deploy commands.** The build check fails closed, and phase 1 itself removes `--env` from the commands in `docs/deploys.md`.
4. **Dependency age.** `@nuxthub/core` is pinned exactly in `bun.lock`. The phase 1 PR notes that its changelog and publish provenance were checked. If a newer release comes out first, wait until it is at least a week old.

If it is cheap, phase 1 also makes the "no new origins in the production output" comparison a CI assertion. The no-third-party end-to-end test already covers the running site.

Two smaller changes come with it:

- **Compatibility flags.** With `nodeCompat`, Nitro adds `no_nodejs_compat_v2` to the generated config, so the Worker runs Nitro's own Node polyfills. We add the same flag to `wrangler.jsonc`, so unit tests run under the flags we deploy with. The unit suite passed with it (276 of 276).
- **Migrations stay SQL in `migrations/db/`.** `hub.db.migrationsDirs` points there, so NuxtHub and Drizzle see the same files. New migrations may be generated by `drizzle-kit generate` into that folder. They are reviewed as SQL like any other, and triggers stay hand-written. The `kinmeet-new-migration` skill is updated in phase 2.

### Order of the migration

None of the phases changes the files that #48, #51, #80 and #91 change in `server/utils/db/` or `server/safeguarding/`. Those PRs merge as they are.

1. **This ADR** (#113). No code.
2. **Phase 1: config and entry** (one ticket, Jun, Security Reviewer and Tech Lead review). Add `@nuxthub/core`, `drizzle-orm` and `drizzle-kit`. Add the `hub` and `$production.nitro.entry` config, `worker/entry.ts`, `main`, `migrations_table`, the compatibility flag, the build check, `db:migrate:local`, and the `--config` in `scripts/d1-migrate.sh`. Add the generated-config check and the `drizzle-kit` hook refusals (conditions 1 and 2), and update `docs/deploys.md` without `--env`. It overlaps the open PRs only in `package.json` and `bun.lock`, so it waits its turn in the one-at-a-time merge queue. **The founder must add the `CLOUDFLARE_ENV` build variable before it merges** (see Consequences). Without it, the build check stops the build and nothing is deployed. Production only builds from the `live` branch, so live is untouched until the next release.
3. **Phase 2: Drizzle schema** (one ticket, after #91 and #51 merge, because they add tables). Write `server/db/schema.ts` for the existing tables, except `safeguarding_items`. Add a test that the schema matches the migrated database, and that `safeguarding_items` is absent from the schema but present in the database. Update the migration skill. New database code uses `hub:db`.
4. **Phase 3, area by area.** A module in `server/utils/db/` moves to Drizzle only when its area is next changed. There is no big rewrite.
5. **Later.** `hub:kv` and `hub:blob` come with the first feature that needs them.

## Options considered

| Option                                                                            | For                                                                                                        | Against                                                                                                                                                  |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adopt with our entry, hand-kept `wrangler.jsonc` and Wrangler migrations (chosen) | Gets `hub:db` and Drizzle; keeps ADR-0008, reviewed bindings and one migration runner; open PRs unaffected | A `CLOUDFLARE_ENV` build variable per Worker (a founder step); generated config to understand; one custom entry file                                     |
| Adopt with NuxtHub defaults                                                       | Least config                                                                                               | Drops the body limits; libSQL in development; `_hub_migrations` would re-run every migration on staging and live; `hub:cache` adds an unreviewed binding |
| Keep `deployConfig: false` and use only NuxtHub's runtime helpers                 | No generated config                                                                                        | Not supported: NuxtHub forces `deployConfig` on                                                                                                          |
| Wait (the #104 recommendation)                                                    | Nothing to change                                                                                          | The founder has decided to adopt now                                                                                                                     |

## Consequences

- **Easier:** typed queries through Drizzle, and less hand-written SQL in new code. Fewer of our own database helpers to maintain, as the existing-modules rule asks.
- **Harder:** a deploy now depends on a build variable as well as the deploy command. The build check guards this, and `docs/deploys.md` must explain it. Reviewers check the generated binding list whenever `hub` config changes.
- **Security and privacy:** the body limits, headers, EU data location and binding review are unchanged. NuxtHub adds a Drizzle Studio route and devtools tab in development only. Devtools stay off (`devtools.enabled: false`), so nothing loads from `local.drizzle.studio`. The production bundle reaches no new origins (the spike output was compared). No `d1-http` driver, so no new API token.
- **Safeguarding:** the safeguarding table stays out of Drizzle and out of NuxtHub's hands, the key stays a secret only the Worker reads, and the hooks are unchanged.
- **Founder steps (through the Head of Delivery), before phase 1 merges.** These follow whatever #116 decides. With #116's single `platform` Worker, `previews` sits inside `env.live`, so there is one build variable, `CLOUDFLARE_ENV=live`, and the build check accepts `live` only. If two Workers stay, it is `staging` on the staging Worker and `live` on the live Worker. No token is needed.
- **Dependencies:** `@nuxthub/core` (Apache-2.0, released 23 October 2026), `drizzle-orm` and `drizzle-kit` (development only), all pinned exactly in `bun.lock`. The core package's changelog and provenance are checked in phase 1 (condition 4).
- **ADR-0008** keeps its decision. Only the wiring described under "Decision" there changes, and phase 1 adds a note to it.
