# Form builders: what we can reuse for forms admins build on the site

- **Author:** Ines Duarte (Research Scout)
- **Date:** 28 October 2026
- **For:** ADR-0010 (Tech Lead), issue #152
- **Rule applied:** [.claude/rules/existing-modules.md](../../.claude/rules/existing-modules.md). Versions were checked on npm on 28 October 2026. Where a claim depends on package behaviour, I read the published package at that version.

## The short version

1. **No free, maintained form _builder_ (the admin editing screen) fits.** The two mature builder UIs, SurveyJS Creator and Vueform Builder, need paid licences. No free Nuxt module provides one. We build the admin editing screen ourselves: a list of fields to add, reorder and edit, plus a preview.
2. **Store each form as our own small JSON definition, and validate it on the server with Zod built from that definition.** This keeps [ADR-0005](../adr/0005-form-validation-with-zod.md) (one validator, stable error codes, lengths in code points). It runs on Workers, because Zod turns off its code generation there. JSON-Schema validators that rely on generated code (Ajv) can't run on Workers or under our CSP.
3. **For the public renderer, FormKit is the one candidate worth an ADR-0010 decision.** It is MIT-licensed and maintained, its schema can be stored as JSON, and its core uses no `eval`. But it fetches its theme and icons from a CDN unless configured not to, and it brings a second validation system. Our own components are the other option.
4. **The bigger questions are not technical.** "Any admin can add any field" clashes with three rules: every field must map to a P3 row, user-facing text must live in the i18n files, and every free-text field needs the SG6 hand-over. ADR-0010 needs an answer to each (see the last section).

Whichever renderer is chosen, the axe scan in `tests/e2e/` covers every route. The Accessibility Reviewer will also test the first built form by hand (#155):

1. keyboard only through every step, including the Change and Leave links;
2. submitting empty puts focus on the summary, each item names its question, and each link focuses its field;
3. hints stay visible and announced while an error shows;
4. errors appear on submit, not on blur;
5. at 320px wide and at 400% zoom, there is no sideways scrolling and the summary is visible;
6. NVDA with Firefox, and VoiceOver on iOS Safari;
7. with reduced motion on, nothing animates or smooth-scrolls;
8. the Turnstile failed and unavailable paths reach the summary (#17).

ADR-0010 settled the list: exactly six types (`short_text`, `long_text`, `email`, `call_name`, `single_choice`, `confirm`). The sketch's multiple choice, yes or no, date and consent are not in it. Any new type needs its own decision. If a date field is ever added, it needs day, month and year inputs in a `fieldset`, not a native picker.

## A shape for ADR-0010 to consider

This is a sketch written before the decision, kept for the record. **Build from [ADR-0010](../adr/0010-generic-forms-and-mail.md), not from this sketch.** In particular, a form does not set its own retention: it names a reviewed P3 purpose from code, and any purpose that allows free text forces the SG6 hand-over.

- **`form_definitions`**: id, slug, status (draft, published, closed), version, and `definition` (JSON). A published version never changes; editing creates a new version, and each submission records the version it answered.
- **The definition** is validated on save by a Zod "meta-schema". It holds:
  - fields from an allow-list of types: short text, long text, email, single choice, multiple choice, yes or no, date, consent;
  - for each field: required, limits, options, and a simple "show if field X equals Y";
  - per-form settings: who can read submissions (a P4 role), retention in days, P3 category, Turnstile and rate-limit settings, and whether a receipt email is sent.
- **The server** builds the Zod schema from the definition and runs the existing `server/utils/forms/process.ts` pipeline. Only the schema source changes. Error codes stay `{ field, code }`.
- **The renderer** is our own field components, or FormKit generated from the definition (above). Either way, no admin-written HTML reaches the page (`security.md`, no `v-html`).

## Clashes ADR-0010 must answer

1. **P3: "Every field you add must map to a row in P3"** ([privacy.md](../../.claude/rules/privacy.md)). With admin-built forms, the team no longer adds the fields. Options: each form carries its P3 category and retention, and publishing needs a Privacy and Safeguarding sign-off role in the app; or only field types from a pre-approved P3 list are allowed. This is for the Head of Delivery and area 5.
2. **i18n: "no hard-coded copy… every string goes through i18n keys"** ([terminology-and-copy.md](../../.claude/rules/terminology-and-copy.md)), and `check:copy` only reads `i18n/locales/`. Admin-written labels live in the database. They need per-locale text in the definition, and the terminology checks (all-ages, group, meet) need to run when an admin saves.
3. **SG6: every free-text route needs a hand-over to the safeguarding lead.** Every long-text field on a built form inherits the "say hello" hand-over action and the go-live condition.
4. **Children writing in** (area 5 open item 1): a generic form can't decide this per form. It needs one rule.
5. **The per-form body limits** ([ADR-0008](../adr/0008-worker-entry-in-front-of-nitro.md), #94) are worked out from fixed schemas today. With built forms, the limit comes from the definition's field limits, with a hard ceiling.
