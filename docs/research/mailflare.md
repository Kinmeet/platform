# Mailflare: what it is, and what porting it would mean

- **Author:** Ines Duarte (Research Scout)
- **Date:** 28 October 2026
- **For:** ADR-0010 (Tech Lead), issue #152
- **Checked against:** [hieunc229/mailflare](https://github.com/hieunc229/mailflare) at commit [`f983977`](https://github.com/hieunc229/mailflare/tree/f9839770f468b0137c781460372a10d949c4f971) (package version 0.5.3), and [mailflare.co](https://mailflare.co), both read on 28 October 2026.

Links into the Mailflare repository are pinned to that commit.

## The short version

1. **Mailflare is not a newsletter or mailing-list tool.** It is a self-hosted Google Workspace replacement: webmail for your own domains, plus calendar, booking pages, file drive and AI agents ([README](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/README.md)). It has no lists, segments, campaigns, double opt-in, preference centre, or bounce and suppression handling. If ADR-0010 needs those, we write them ourselves or find another tool. Mailflare's data model doesn't help there.
2. **It is AGPL-3.0** ([LICENSE](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/LICENSE)). We may read it and reimplement its ideas. We may not copy or translate its code into our repository unless the whole platform is released under the AGPL. That would contradict our [NOTICE](../../NOTICE.md) ("no licence granted"). That is the founder's call, and this is not legal advice.
3. **It runs on the same Cloudflare products we use, and more.** Workers, D1, R2, Queues, a Durable Object, Email Routing, the `send_email` binding, Workers AI and Cloudflare Images. But it is a React app on vinext (Next.js on Vite), so a "port to Nuxt" means rewriting the whole UI and server, not moving code across.
4. **Several features break our firm rules** and would have to be left out or changed. These are open tracking pixels with location, remote images loading by default, IP addresses and user agents in the audit log, third-party AI providers, push services, licence checks with a payment provider, and an account-wide API token.

## How it is built

- **Framework:** React 19 on [vinext](https://github.com/cloudflare/vinext) (Next.js API on Vite), Radix UI, Tailwind, TanStack Query ([package.json](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/package.json)). There is no Vue or Nuxt code to reuse.
- **Worker entry:** one `worker.ts` with `fetch`, `email` (Email Routing inbound), `queue` and `scheduled` handlers ([worker.ts L34-L141](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/worker.ts#L34-L141)).
- **Bindings** ([wrangler.jsonc](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/wrangler.jsonc)):
  - D1 `DB`, with Drizzle migrations in `drizzle/migrations`. A schema "kit" also targets Postgres, MySQL and Turso ([kits.ts](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/src/db/schema/kits.ts));
  - R2 `BUCKET` for raw MIME and attachments;
  - three Queues: inbound, outbound and agent;
  - a Durable Object `RealtimeHub` for live updates;
  - `send_email` `EMAIL`, Workers AI `AI` (remote), and Images `IMAGES`;
  - three rate-limit bindings, and crons at 02:00 daily and every 5 minutes.
- **Cloudflare API token:** setup needs a runtime `CF_TOKEN` with account-wide Email Sending, DNS and Email Routing permissions on **all accounts** and **all zones** ([README](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/README.md#deploy)).
- **Data model:** 52 tables in [`src/db/schema/index.ts`](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/src/db/schema/index.ts). The core is `users`, then `domains`, then `mailboxes` (with `mailbox_aliases` and `mailbox_access`), then `messages` (with `folders`, `message_attachments` and `outbound_jobs`). Around that sit `routing_rules`, `contacts`, `email_templates`, `calendar_events`, `booking_events`, `drive_items`, `webhooks`, `api_keys`, `sessions` (token hash only), `audit_logs`, `backups`, and the `agent_*` and `jmap_*` tables.

## What is worth borrowing as ideas

These are ideas only; see the licence section.

- **Email Routing, then a Queue, then D1 and R2** for inbound mail ([worker.ts L59](https://github.com/hieunc229/mailflare/blob/f9839770f468b0137c781460372a10d949c4f971/worker.ts#L59)). Keeping the `email()` handler short and retrying in a queue fits our runtime well.
- **An outbound Queue**, so the `send_email` call never sits in a request. That is close to ADR-0006's `waitUntil`, but a queue gives retries.
- **Routing rules as data** (scope, match field, operator, action, priority). This is a good shape for "send applications for group X to inbox Y".
- **Webhooks with a delivery log and retries**, if the Discord bot ever needs push rather than pull.
- **Per-capability admin flags** (`canManageDomains`, `canManageUsers`, `canManageMailboxes`). These map well onto P4 roles.

## Open questions for ADR-0010

1. **Which part of Mailflare does the founder want?** Shared inboxes for role addresses (safeguarding@, hello@)? Booking pages? Or mailing lists and newsletters, which Mailflare does not have? The answer decides most of the data model.
2. **Licence.** Is the platform staying "no licence granted"? If so, everything is a clean reimplementation and no Mailflare code is used.
3. **Mailboxes need P3 rows** (messages, attachments, contacts, audit) and an SG6 hand-over before any inbox takes real mail.
